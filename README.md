# HMCTS Dev Test Backend

A Spring Boot service (Java 21) backing a case management system, exposing an example case API and a database-backed health endpoint.

## Run locally with Docker Compose

The stack is the application plus a PostgreSQL 16 database. Credentials are passed
through environment variables; nothing is hardcoded.

```bash
cp .env.example .env      # adjust the values if you want; defaults work for local runs
docker compose up --build
```

The app is published on the port set by `SERVER_PORT` (default 4000). Compose waits
for Postgres to be healthy (`pg_isready`) before starting the app, and the app has
its own healthcheck against `/health`.

Verify database connectivity:

```bash
curl localhost:4000/health
```

A healthy response is `"status":"UP"` with a `db` component reporting `PostgreSQL`.
Stop the stack with `docker compose down`.

`.env` is gitignored; `.env.example` is the committed template.

## CI/CD pipeline

One workflow, [.github/workflows/ci.yml](.github/workflows/ci.yml), runs on pull
requests and on pushes to `main`. Feature branches are gated through their PR;
`main` runs on merge and is the only branch that produces the `latest` image tag.

| Stage | What it does | What it blocks on |
|-------|--------------|-------------------|
| Build, test & Checkstyle | `./gradlew build` — compiles, runs unit + integration tests, and runs Checkstyle (via the `uk.gov.hmcts.java` plugin) | Any compile error, test failure, or Checkstyle violation |
| Image build & Trivy scan | Builds the Docker image tagged with the short git SHA (and `latest` on `main`), then scans it | A **fixable CRITICAL** vulnerability fails the job; **HIGH** findings are reported but do not fail |
| Terraform fmt & validate | `terraform fmt -check` and `terraform validate` against `terraform/` | Unformatted or invalid Terraform |

**Image tagging.** Every image is tagged with the short commit SHA, giving an
immutable, traceable link from a running image back to the exact commit. `latest`
is only applied on `main` as a convenience pointer to the newest release build.
There is no registry push in this pipeline (no registry is configured); a push
step would slot into the image job, gated to `main`.

**Trivy.** The scan runs twice — once blocking on CRITICAL, once reporting HIGH.
`ignore-unfixed` is enabled so the pipeline blocks only on vulnerabilities that
actually have a fix available, rather than going permanently red on an unpatchable
base-image CVE.

## Terraform (Azure)

`terraform/` provisions the service on Azure. It is validate-only here — no state
is created and no account is required.

Resources:

- Resource group
- Azure Database for PostgreSQL Flexible Server, plus the application database
- Azure Container Apps (environment + app) running the container image
- Azure Key Vault holding the database password

**Why Container Apps:** scale-to-zero, per-revision traffic splitting, and a
simpler fit than AKS for a single service — with better container support than
App Service.

**Secrets.** The database password is generated by a `random_password` resource
and written straight into Key Vault. It is marked sensitive and never appears in
plain text, in outputs, or in a `.tfvars` file. The Container App reads it at
runtime via a Key Vault secret reference, using a user-assigned managed identity
that holds read-only access to the vault.

### How it would be deployed for real

`terraform validate` runs without credentials because the `azurerm` backend block
in `providers.tf` is commented out and it validates with `-backend=false`.

In production, state would live in an Azure Storage account rather than locally:

- A storage account + blob container hold the `terraform.tfstate`.
- State locking is provided by the blob lease, so concurrent applies cannot corrupt state.
- The commented `backend "azurerm"` block in `providers.tf` is uncommented, and
  `terraform init` is run with the backend configured.

Deployment would then be `terraform init` → `plan` → `apply` with an authenticated
Azure principal (a service principal in CI), passing `container_image` set to the
SHA-tagged image built by the pipeline.

## Assumptions and trade-offs

- **Default branch is `main`.** The pipeline's `latest` tagging and release gate
  key off `main`; rename the repository default branch from `master` to `main`.
- **jdbc, not JPA.** I added `spring-boot-starter-jdbc` and the PostgreSQL driver.
  The commented `spring.jpa` block in `application.yaml` stays commented because
  Hibernate is not on the classpath.
- **Postgres has public network access enabled** in Terraform for simplicity.
  Production should use a delegated subnet or private endpoint with firewall rules
  and no public access.
- **Key Vault uses access policies**, not RBAC. Access policies are self-contained;
  RBAC role assignments are the more modern option but require role-assignment
  rights on the deployer.
- **No image registry.** The pipeline builds and scans locally; wiring a push to
  ACR or GHCR is a small, self-contained addition.
- **Names are derived from `project`/`environment`.** Variable validations keep
  them within Azure limits; Key Vault and Postgres names must also be globally
  unique, which the deployer is responsible for.
